# 사용자·관리자 앱 분리 계획

작성: 2026-09-10. 상태: 로컬 분리·검증 완료. 운영 전환은 미실행.

## 목적과 유지할 동작

- Git 루트, 원격 저장소, 현재 브랜치를 유지한다. 기존 소개 화면의 미커밋 변경을 보존한다.
- 사용자 앱은 `apps/client`(:3000), 관리자 앱은 `apps/admin`(:3001)로 독립 실행·빌드한다.
- 사용자 URL을 유지하고 관리자 앱에서도 `/admin` 경로를 우선 유지한다. 사용자 앱의 예전 관리자 주소는 설정된 관리자 주소로 이동시킨다.
- 운영 DB 구조·데이터·배포 설정은 이번 로컬 분리 과정에서 변경하지 않는다. 배포 전환 절차와 복구 절차를 문서화한다.

## 작업 순서

1. **이전 전 기준 확보**: 현재 변경 파일과 소스 사본 보존, 기존 테스트 실행, 테스트 전용 DB 준비, 기존 앱의 사용자·관리자 화면 캡처.
2. **워크스페이스 구성**: 앱 소스를 이동하고 루트 실행 명령, 잠금 파일, 앱별 환경 설정·빌드 설정을 정리한다.
3. **공용 코드 분리**: 순수 타입·검증은 shared, 접속 팩토리·생성 DB 타입은 database, 재사용 화면·테마는 ui로 이동한다. 앱 사이 직접 참조와 공용 코드의 앱 역참조를 금지한다. 관리자와 운영 스크립트가 공유하는 외부 콘텐츠 수집은 순수 shared와 분리한다.
4. **앱 경계 수정**: 로그인 쿠키, 관리자 권한, 이전 주소 연결, 사용자 전자책 접근, 콘텐츠 갱신, 이미지·폰트·스타일 경로를 점검한다.
5. **검증과 수정**: 아래 행렬을 실제 실행하고 실패 원인을 수정한다. 이전 화면을 기준으로 비교하며, 실패를 숨기기 위해 기준 이미지를 새 화면으로 덮어쓰지 않는다.
6. **결과 정리**: 검증 명령·결과·증거와 남은 외부 의존성을 기록하고 배포 순서·복구 절차를 제공한다.

## 테스트 행렬

| 종류 | client | admin |
|---|---|---|
| E2E 런타임 | 피드·탐색·상세·읽기·로그인 유도·프로필·상호작용·기존 관리자 링크 | 로그인·로그아웃·권한 차단·도서·게시물·채널·추천·미리보기 |
| 인테그레이션 | 실제 테스트 DB 조회, 인증 세션, 접근 정책, 비공개 전자책 주소, 사용자 기록 | 실제 테스트 DB 생성·수정·조회·정리, 권한 검증, 관리자 수정의 사용자 앱 반영 |
| 디자인 회귀 | 기존 화면과 모바일 375px 기준 비교, 주요 화면·시트·테마, 필요한 데스크톱 확인 | 기존 로그인·목록·폼·카드 미리보기와 데스크톱 기준 비교 |
| 공통 | 두 앱 프로덕션 빌드, 기존 순수 테스트, 타입 검사, 패키지 의존 경계, 브라우저·서버 오류 확인 | 동일 |

테스트는 로컬 Supabase와 전용 계정·데이터를 기본으로 사용한다. 실서비스 DB를 초기화하거나 운영 콘텐츠를 수정하지 않는다. 로컬 환경이 불가능하면 가능한 대체 환경을 조사하고 실제 연동 검증 여부를 명시한다. OAuth 공급자의 사용자 동의 등 자동화할 수 없는 외부 단계는 테스트 범위와 구별한다.

## 배포 원칙

기존 Vercel 사용자 프로젝트·도메인을 유지하고 빌드 루트를 `apps/client`로 전환한다. 관리자용 프로젝트를 같은 저장소의 `apps/admin`에 연결한다. 관리자 URL과 앱별 환경 설정을 등록하고 검증한 다음 기존 관리자 주소를 전환한다. DB·카드 형식을 바꾸지 않아 구버전 사용자 앱과 호환되므로 새 관리자를 먼저 검증하고 사용자 프로젝트를 전환한다. 두 배포는 동시에 원자적으로 바뀌지 않는다는 전제로 복구 경로를 준비한다.

## 실행 기록

- 초기 확인: 기존 단일 앱, master 브랜치, 소개 화면 미커밋 변경 존재.
- 운영 Vercel 조회는 이전 검토에서 권한 오류가 발생했다. 운영 설정 확인·전환은 미실행 상태.
- 기존 문서의 순수 함수 테스트 제한은 이번 사용자의 명시적 E2E·인테그레이션·디자인 회귀 테스트 요청으로 확장한다.
- Docker 소켓 오류 복구, 별도 테스트 DB의 24개 마이그레이션 적용, 공용 패키지·두 앱 분리를 완료했다.
- 최종 결과: E2E 13/13, 실제 DB 7/7, 디자인 비교 24/24, 단위·경계 검사 298/298, 두 앱 빌드·타입 검사 통과. 자세한 결과와 기존 검사 오류는 [결과 보고서](./monorepo-verification-report.md)에 기록했다.
