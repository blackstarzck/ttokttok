# 릴스 재생·전환 최적화 조사와 적용

조사·적용일: 2026-09-10. 게시물 추천 순위를 바꾸는 작업이 아니라, 선택한 영상을 빨리 보여주기 위한 로드·재생 관리다.

후속 조사: [Instagram·TikTok·YouTube 비교와 원본 보호·전송 개선 제안](./shortform-video-delivery-plan.md). 후속 문서는 제안이며 이 문서의 구현 완료 범위와 구분한다.

## 공식 자료에서 확인한 원리

| 자료 | 확인한 내용 | 똑똑에 적용하는 범위 |
|---|---|---|
| [Meta: Reels의 AV1 도입](https://engineering.fb.com/2023/02/21/video-engineering/av1-codec-facebook-instagram-reels/) | 같은 영상을 여러 비트레이트로 변환하고 연결에 맞춰 선택한다. 압축 효율도 전송량을 줄이는 수단이다. | 현재 단일 MP4 업로드에는 화질별 변환·적응형 스트리밍이 없다. 이 부분은 별도 서버 처리 과제로 남긴다. |
| [Google Android: Media3 미리 읽기](https://android-developers.googleblog.com/2025/09/introducing-preloading-with-media3.html) | 다음 콘텐츠를 미리 준비하고, 현재 재생과의 경쟁을 줄인다. 위치에 따라 준비 우선순위를 바꾸고 멀어진 항목은 해제한다. | 현재 재생을 우선하며 이동 방향의 인접 영상 하나만 준비한다. 불필요해진 영상의 로드를 해제한다. |
| [Google Android: PreloadManager 심화](https://android-developers.googleblog.com/2025/09/a-deep-dive-into-media3-preloadmanager.html) | 일정 범위의 콘텐츠만 유지하고 준비 결과를 재사용하는 관리가 필요하다. | 이미 준비된 이웃 영상이 선택되면 같은 재생기를 유지한다. 화면의 마운트 범위와 영상 다운로드 범위를 구분한다. |
| [YouTube IFrame API](https://developers.google.com/youtube/iframe_api_reference) | 플레이어 준비와 실제 영상 다운로드는 다르다. 자동재생 차단 이벤트와 재생 상태를 제공한다. | 이웃 플레이어는 자동재생 없이 준비하고 활성 영상만 재생한다. 차단·오류 때 실제 플레이어 UI를 노출한다. |

Google의 자료는 숏폼 앱을 위한 공개 개발 지침이다. **YouTube Shorts 서비스 내부에서 사용하는 정확한 미리 읽기 개수·알고리즘이 공개됐다는 근거는 아니다.** 아래 수치는 똑똑에 적용한 보수적인 정책이며, Instagram·Shorts의 수치를 복제한 것이 아니다.

## 적용 정책

- 현재 영상이 실제 재생 중이고 앞으로 3초(짧은 영상은 남은 길이)가 확보됐을 때, 같은 게시물에 250ms 이상 머물렀으면 이동 방향의 이웃 하나를 준비한다. YouTube는 API의 로드 비율을 이용한 보수적 추정이다.
- 화면에 60% 이상 보이고 브라우저 탭이 활성 상태이며 시트에 가려지지 않은 영상만 재생한다. 빠르게 지나간 항목·이전 요청의 늦은 응답이 재생 상태를 뒤집지 않게 한다.
- 데이터 절약 모드, 3G 이하로 보고된 연결, 오프라인, 숨겨진 탭에서는 추측성 미리 읽기를 중단한다. 연결 정보 API가 없는 브라우저는 한 개 제한을 기본으로 한다.
- MP4는 활성 영상과 선택된 이웃 외의 소스를 분리하고 로드를 취소한다. 화면의 앞뒤 두 항목 마운트는 유지하되, 모두 다운로드하지 않는다. 현재 마운트 범위에서 사용자가 직접 누른 일시정지를 존중한다.
- MP4가 500ms 이상 지연되면 안내를, 8초 이상이면 재시도를 표시한다. 다운로드 실패·자동재생 차단도 조작 가능한 버튼을 표시한다. YouTube의 실제 재생 이후 덧붙이던 700ms 가림을 제거한다.

## 남은 한계와 다음 단계

브라우저의 [영상 preload 속성](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/video)은 힌트다. MP4를 정확히 몇 초·몇 바이트만 받도록 보장하지 못하며 이웃 한 편이 통째로 다운로드될 수 있다. 현재 버퍼 조건도 전송 대역폭의 독점 우선순위를 보장하지 않는다. 운영 회선에서 첫 재생 시간·재버퍼링·전송량을 측정해 수치를 조정해야 한다.

고화질 원본의 전송 부담을 해결하려면 업로드 이후 화질별 영상·짧은 구간·썸네일을 만들고, 연결에 따라 화질을 선택하는 스트리밍(HLS 등)을 연결해야 한다. Meta 자료에서 확인한 적응형 전송 원리를 적용하는 다음 단계다. 이번 작업에는 인코딩 서비스, 저장 구조, 업로드 화면 변경을 포함하지 않았다.

YouTube는 외부 플레이어이므로 미리 읽는 미디어 구간·화질·광고를 앱이 직접 제어하지 않는다. 공식 임베드만 사용하며 Shorts 앱과 동일한 시작 속도를 보장하지 않는다. 실제 모바일 Safari·Android, 긴 운영 영상, 해외 회선에서 추가 확인이 필요하다.

## 재현 검증

`e2e/client.video.spec.ts`는 격리된 로컬 DB에 임시 게시물을 생성하고 종료 시 해당 게시물·파일만 정리한다. 1080×1920, 6초의 실제 MP4를 사용한다. 현재 영상의 응답 지연, 인접 한 개 제한, 빠른 전진·역방향 이동, 수동 정지 유지, 데이터 절약, 다운로드 실패 후 복구, 제한된 연결을 검사한다. 테스트용 합성 영상이며 운영 영상 전체의 성능을 대표하지 않는다.

확인 결과: 단위 테스트 302개, 두 앱 기능 E2E 19개(영상 관련 5개 포함), 실제 DB 연동 7개, 화면 회귀 24개 통과. 최종 재생 정책 수정 후 영상 5개를 다시 실행했다. 375px에서 대기 안내·재생 화면을 직접 확인했다. YouTube 항목은 가짜 API를 통한 호출 규약 검증이며 실제 YouTube 네트워크 성능 측정이 아니다.

제한 연결 실험은 약 9.27MB/6초 합성 영상을 8Mbps, 지연 120ms 조건으로 진행했다. 브라우저는 이웃 영상을 약 0.233초만 준비한 경우에도 선택 후 재생을 시작했다. 이 수치는 **미리 읽기 양을 브라우저가 결정한다는 사례**이며 속도 개선율을 증명하는 전후 비교나 운영 환경 보장은 아니다.
