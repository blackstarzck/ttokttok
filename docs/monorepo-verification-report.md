# 사용자·관리자 분리 결과

검증일: 2026-09-10. **로컬 분리와 아래 검증을 완료했다. 운영 배포는 실행하지 않았다.**

## 무엇이 달라졌나

- Git 루트·remote·master 브랜치는 그대로다. 사용자 앱은 `apps/client`(3000), 관리자는 `apps/admin`(3001)에서 독립 실행·빌드한다. 루트에서 `npm run dev`로 함께 실행한다.
- 공용 타입·검증, DB 접속·생성 타입, 화면·테마를 각각 shared·database·ui 패키지로 분리했다. 외부 EPUB 수집은 네트워크를 쓰므로 추가한 content 패키지에 둔다. 앱끼리 직접 참조하지 않는다.
- 사용자 로그인은 기존 쿠키를 유지하고 관리자 로그인은 별도 쿠키를 쓴다. 예전 `/admin` 주소는 관리자 앱으로 연결된다. 두 앱은 같은 DB를 사용하며 관리자 저장 후 사용자 앱의 다음 요청에서 변경을 읽는다.
- 사용자가 수정 중이던 소개 페이지는 공용 로고의 import 경로 외에 그대로다. 원본 정적 자산 9개를 바이트 단위로 비교해 보존을 확인했다. 운영 DB와 기존 로컬 개발 DB를 초기화하지 않았다.

## 최종 검증

각 테스트는 실패를 수정한 뒤 다시 실행했다. 최종 실행에 재시도·건너뛰기는 없다. 테스트 성공은 아래 범위의 결과이며 모든 가능한 환경에서 버그가 없다는 보장은 아니다.

| 검증 | client | admin | 결과 |
|---|---:|---:|---|
| 실제 브라우저 E2E 런타임 | 5 | 8 | 13/13 통과 |
| 실제 로컬 DB 인테그레이션 | 4 | 3 | 7/7 통과 |
| 분리 전 화면과 디자인 비교 | 13 | 11 | 24/24 통과 |
| 프로덕션 빌드 | 통과 | 통과 | 두 앱 통과 |
| 타입 검사 | 통과 | 통과 | 공용 패키지도 통과 |
| 순수 함수·패키지 경계 검사 | 공통 | 공통 | 298/298 통과, 기존 280개 포함 |

브라우저 검증은 Windows의 Chromium, 실제 로컬 Supabase와 작성한 테스트 전자책·영상으로 수행했다. API 모킹으로 연동을 대신하지 않았다. 좋아요·댓글·찜·독서 기록 저장, 실제 영상 재생, EPUB 본문 열기, 관리자 권한 차단, 두 로그인 세션 독립, 발행/비공개 전환, 업로드 후 사용자 읽기, 채널 CRUD, 추천 노출, 신고 처리를 확인했다.

디자인 기준 24개는 분리 전 소스(`2e0c6b5` + 소개 페이지의 기존 미커밋 변경)를 따로 빌드한 3100 서버에서 캡처했다. 최종 비교는 분리 후 3000·3001 서버를 사용했다. 실패를 없애려고 분리 후 화면을 기준으로 저장하지 않았다. 중간 실패가 남긴 테스트 채널을 정리한 뒤 같은 원본 앱에서 기준을 다시 캡처하여 데이터 조건을 맞췄다. 픽셀 차이 허용치는 0.1%다. 실제 최종 사용자 홈과 관리자 편집 화면도 별도로 캡처해 확인했다.

브라우저 배포 파일은 client 31개·admin 23개를 검사하여 테스트 서버 비밀 키가 없음을 확인했다. 빌드 경로 목록에서 사용자 앱에 관리자 구현이, 관리자 앱에 사용자 페이지·인증 콜백·뷰어가 포함되지 않음을 확인했다.

## 검증 중 찾아 수정한 문제

- 관리자의 서비스/게시물 보기 링크가 기존 상대 경로를 사용하던 부분을 수정했다. 발행한 글은 사용자 앱으로, 임시저장 글은 관리자 편집 미리보기로 연결한다.
- 비활성 미리보기 안의 링크가 사용자 경로를 관리자 서버에서 미리 요청해 발생하던 404를 없앴다. 미리보기는 클릭·집계뿐 아니라 링크 사전 요청도 실행하지 않는다.
- 앱별로 쿠키 이름과 서버·브라우저·요청 처리 설정을 일치시켰다. 일반 사용자의 관리자 접근에서 이동이 반복되지 않고, 관리자 로그아웃 후 사용자 로그인이 유지됨을 검증했다.
- 공용 UI의 클릭·참조 전달, 공용 스타일 탐색과 폰트·이미지 경로, 서버 데이터 조회와 생성 타입, 앱별 빌드·실행·테스트 경로를 정리했다.
- 반복 테스트에서 댓글이 중복되고, 저장 완료 전에 다음 화면을 검사하던 테스트도 정리했다. 최종 테스트는 실제 저장 결과를 확인한 뒤 진행한다.

## Docker 및 테스트 데이터

Docker Desktop의 기존 소켓 오류를 해결했다. Docker를 정상 종료한 뒤 정확한 실행 소켓 디렉터리를 백업하고 다시 만들었다. 설정·이미지·볼륨 초기화는 하지 않았다. 백업은 `C:\Users\admin\AppData\Local\Docker\run-backup-ttokttok-20260910*` 및 `C:\Users\admin\AppData\Local\docker-secrets-engine-backup-ttokttok-20260910*`에 남아 있다.

테스트 전용 프로젝트는 `ttokttok-e2e`, API 포트는 54421이다. 저장소의 마이그레이션 24개를 적용했으며 기존 `ttokttok` 개발 DB와 별도 볼륨을 사용한다. 테스트 명령은 정확히 이 로컬 주소만 허용한다. 로컬 Supabase 실행 파일 누락도 프로젝트 개발 의존성으로 복구했다.

## 남은 확인 사항

- **운영 전환은 별도 작업이다.** Vercel 프로젝트 조회가 403으로 거부되어 운영 설정을 확정하지 못했다. 기존 사용자 도메인을 유지하면서 두 앱의 빌드 루트, 공용 소스 포함, 환경 변수와 관리자 도메인을 설정해야 한다. 관리자는 전환 후 한 번 다시 로그인한다. [배포 영향·순서·복구](./monorepo-deployment.md)를 따른다.
- 외부 Google/Kakao의 동의 완료, 외부 EPUB 수집 서비스 가용성, 실제 운영 도메인의 세션·콜백은 로컬 테스트 범위 밖이다. 사용자 인증 이후 기능은 실제 로컬 인증 세션으로 검증했다.
- 전체 코드 검사(`npm run lint`)는 **오류 7개·경고 2개로 미통과**다. 분리 전 소스에도 같은 규칙의 오류 7개·경고 2개가 있었다. 관리자 추천 문구의 따옴표, 기존 댓글·영상·뷰어·테마의 상태 처리, 기존 미사용 항목에 해당하며 이번 분리에서 새 검사 위반은 남기지 않았다.
- 빠른 페이지 이동 시 Next 서버의 `The destination stream closed early` 진단이 발생했다. 원본 앱에 동일한 E2E 탐색을 실행해 같은 진단과 성공 결과를 재현했다. 원인 전체를 수정했다는 뜻은 아니며, 최종 E2E에는 예기치 않은 브라우저 실행 오류나 실패 HTTP 응답이 없었다. EPUB의 스크립트 금지 프레임 진단도 원본에서 동일하게 확인했고 보안 설정을 완화하지 않았다.
