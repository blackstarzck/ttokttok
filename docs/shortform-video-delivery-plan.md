# 숏폼 플랫폼 조사와 똑똑 영상 전송 제안

> 2026-09-11 최종 결정으로 아래 제안 중 관리형 SaaS·비공개 원본·퍼가기 방어는 적용하지 않는다. 현재 구현은 **PC 무료 변환 → ZIP 하나 업로드 → 기존 Supabase에서 자동 화질 재생**이다. 현행 운영·배포·검증 절차는 [영상 운영 안내](./video-operations.md)를 따른다. 아래는 조사 당시의 비교 기록이다.

조사일: 2026-09-10. 이 문서는 적용 제안이다. 자동 변환·비공개 원본 이관·외부 서비스 가입·배포는 실행하지 않았다. 이전에 적용한 브라우저 재생 관리는 [릴스 최적화 기록](./reels-playback-optimization.md)을 참조한다.

## 1. 플랫폼별 확인된 내용과 한계

| 대상 | 공개 자료에서 확인한 방식 | 똑똑에 가져올 원리 |
|---|---|---|
| Instagram/Facebook Reels | 업로드 영상을 여러 해상도·비트레이트로 변환하고 연결에 따라 선택한다. 영상별 시청량 예측에 따라 더 정교한 압축에 쓸 연산량도 조절한다. [Meta 기술 글, 2023-02-21](https://engineering.fb.com/2023/02/21/video-engineering/av1-codec-facebook-instagram-reels/) | 원본을 그대로 재생하지 않고 재생용 버전을 만든다. 초기에는 적은 수의 화질로 시작한다. |
| TikTok | 네트워크 상태와 영상의 복잡도를 고려해 화질 구성을 최적화하는 TLadder를 공개했다. [TikTok 공식 발표, 2025-03 행사](https://developers.tiktok.com/blog/developers-stanford-digital-innovation) | 움직임이 많은 영상과 정적인 도서 소개 영상에 동일한 전송량을 강제하지 않는다. 샘플별 가독성과 움직임을 검사한다. |
| TikTok Minis | 앞부분 데이터를 메모리에 준비하고 재생할 때 재사용한다. 순서가 있는 목록의 인접 항목 준비, 취소·정리, 준비 데이터가 실제 사용됐는지 측정을 지원한다. [공식 플레이어 문서, 2026-08-04 갱신](https://developers.tiktok.com/docs/en/minis-player) | 다음 영상의 앞부분만 제한적으로 준비하고 건너뛴 요청은 취소한다. 이 문서는 미니 드라마용으로 일반 For You 피드의 현재 내부 구현과 동일하다고 단정하지 않는다. |
| YouTube | 업로드 영상을 기기에 적합한 재생용 영상으로 압축·변환한다. 연결 속도·화면·원본 품질 등 시청 조건에 맞춰 재생 화질을 조절한다. [YouTube 기술 글, 2021-04-21](https://blog.youtube/inside-youtube/new-era-video-infrastructure/), [공식 화질 안내](https://support.google.com/youtube/answer/91449?hl=en) | 자동 변환과 연결에 맞춘 화질 선택을 적용한다. 해당 자료는 YouTube 공통 기반 설명이며 Shorts의 정확한 선행 다운로드 개수·시간을 공개한 자료가 아니다. |

보조 근거로 [NSDI 2023의 Dashlet 연구](https://www.usenix.org/system/files/nsdi23-li-zhuqi.pdf)는 당시 TikTok의 앞부분 다운로드와 화질 선택을 측정했다. 구버전 관찰이므로 현재 틱톡의 고정 정책이나 똑똑의 정답으로 사용하지 않는다. 게시물 추천 알고리즘과 영상 다운로드 순서 결정은 별개이며, 이번 요구는 후자에 해당한다.

다운로드 버튼 정책을 원본 저장소 보호의 증거로 사용하지 않는다. 플랫폼별 원본 저장소 권한·보존 방식 전체가 위 문서에 공개된 것은 아니다. 똑똑의 원본 분리는 사용자 요구와 현재 코드 점검에 근거한 설계 제안이다.

## 2. 현재 프로젝트와의 차이

- 관리자는 업로드 파일을 공개 videos 저장소에 저장하고, 사용자 화면에는 그 파일의 공개 주소가 전달된다. 자동 압축·화질별 변환 과정이 없다. 근거: 관리자 posts/actions.ts의 영상 저장 처리와 20260827000003_rls_storage.sql의 공개 설정·읽기 정책. 운영 저장소 설정을 별도 조회한 결과는 아니며 저장소 코드 기준이다.
- 현재 영상 재생 우선, 이동 방향의 이웃 한 개 준비, 느린 연결에서 미리 읽기 축소, 화면 밖 정지·소스 해제, MP4 지연 안내·재시도는 이전 작업에서 적용했다. 다운로드하는 원본의 크기를 줄이는 단계는 아직 없다.
- 기본 전송 캐시는 이미 Supabase Storage가 제공한다. 따라서 단순히 CDN을 추가하는 것만으로 해결될 문제로 보지 않는다. [Supabase CDN 설명](https://supabase.com/docs/guides/storage/cdn/fundamentals)
- 일반 MP4의 preload는 브라우저 힌트다. 3초 버퍼 조건은 현재 영상의 준비 상태이며 다음 영상을 정확히 3초만 받도록 강제하는 기능이 아니다. 짧은 구간 단위의 스트리밍으로 전환하면 준비량을 더 명확히 관리할 수 있다.

## 3. 권장 구조

관리자 원본 업로드 → 비공개 저장 → 별도 영상 처리 → 여러 화질의 재생용 영상·썸네일 생성 → 준비 완료 확인 → 게시 → 사용자에게 재생용 구간만 전달.

**원본 보호:** 일반 사용자·비회원은 원본 저장소 읽기 권한을 갖지 않는다. 원본 주소나 원본을 열 수 있는 임시 주소를 사용자 화면·피드 응답에 보내지 않는다. 관리자와 영상 처리 작업만 원본을 읽는다. 원본의 임시 재생 주소를 사용자에게 주는 방식은 이 요구를 충족하지 않는다. 재생용 복사본의 추출 방지는 별도 문제이며 이번 요구만으로 DRM을 필수화하지 않는다.

**영상 처리:** 초기 실험은 세로 영상의 짧은 변 기준 480·720·1080 화질, 최대 원본 해상도까지만 생성하는 구성을 후보로 한다. 숫자는 플랫폼 복제값이나 확정값이 아니다. 텍스트 가독성과 움직임을 보고 압축 수준을 조정한다. 높은 해상도 원본도 처음부터 최고 화질을 강제하지 않는다. 여러 화질과 구간 전송을 제공하는 HLS를 우선 검토한다. 관리형 서비스가 화질 구성을 정하는 경우 실제 생성 결과와 지원 범위를 확인한다.

**재생:** 가벼운 첫 구간으로 시작하고 여유가 생기면 화질을 높인다. 기존 스크롤·일시정지 정책은 유지한다. 다음 이웃의 초기 구간만 준비하고 빠르게 지나간 영상의 준비는 취소한다. 구간 길이와 준비량은 2초 안팎부터 실험하되 확정값으로 주장하지 않는다. 너무 짧으면 요청 수와 관리 비용이 늘어난다. 준비한 재생기를 활성 전환 때 재사용하며 원본 MP4로 돌아가는 우회 재생은 두지 않는다.

**관리 경험:** 원본 파일만 올리면 된다. 업로드 중·영상 준비 중·게시 가능·처리 실패를 보여주고, 처리되지 않은 영상은 피드에 게시하지 않는다. 새 영상으로 교체할 때는 새 버전이 준비된 뒤 연결을 바꿔 재생 도중 파일이 달라지지 않도록 한다. 첫 화면 이미지는 자동 생성하며 로딩 중 빈 화면을 줄이는 역할이다.

**전송 권한:** 필요하면 발행된 재생용 영상에만 만료되는 재생 권한을 발급한다. 비회원 시청도 유지할 수 있다. 스트리밍 목록뿐 아니라 구간 파일도 같은 접근 정책으로 보호하고, 재생 중 권한 만료 시 자연스럽게 갱신한다. 이는 주소의 장기 공유·무단 접근을 줄이는 기능이며 시청자의 복사 방지 보장은 아니다. 캐시 효율은 별도로 점검한다. [서명 재생 예시](https://www.mux.com/docs/guides/secure-video-playback), [서명 주소와 캐시](https://supabase.com/docs/guides/storage/cdn/smart-cdn)

## 4. 프로젝트에 맞는 구현 선택

추천은 **기존 Supabase는 계정·게시물·비공개 원본을 맡고, 영상 변환·배포는 관리형 영상 서비스에 맡기는 구성**이다. 현재 두 웹 앱의 일반 저장 요청 안에 무거운 영상 변환을 넣지 않고, 업로드와 처리 완료 통지를 분리한다. 운영 규모가 확인되지 않은 상태에서 플랫폼 수준의 자체 인코딩 시스템을 구축하는 부담을 줄이기 위한 판단이다.

| 선택 | 적합성·확인할 점 |
|---|---|
| 관리형 서비스 | 자동 변환·적응형 재생·전송을 함께 제공하는 [Cloudflare Stream](https://developers.cloudflare.com/stream/) 등이 후보다. 한국 모바일 회선 품질, 세로 영상 결과, 첫 재생 시간, 저장·시청량 비용, 원본 보존·삭제 정책을 샘플로 비교한 뒤 선택한다. 서비스 도입은 아직 확정하지 않았다. |
| 자체 처리 작업 + 저장소 | 변환 도구·별도 작업 서버·작업 대기열·실패 재시도·재생 구간 배포를 운영한다. 압축·비용 통제가 중요해지는 경우의 대안이다. 웹 앱의 요청 처리와 분리해야 한다. |

외부 서비스를 사용해도 현재 도서 정보·좋아요·댓글·릴스 화면은 유지할 수 있다. 업로드 영상의 재생 경로를 바꾸는 작업이다. YouTube 임베드는 기존 공식 플레이어를 유지하며, 그 영상 파일을 추출하거나 똑똑에서 다시 변환하지 않는다.

## 5. 적용 순서와 완료 기준

1. 샘플 운영 영상으로 변환·모바일 재생을 비교하고 구현 경로를 선택한다. 현재 방식도 같은 조건으로 측정해 전후 비교 기준을 만든다.
2. 비공개 원본 저장과 자동 처리·게시 상태를 연결한다. 실패·재시도·영상 교체·삭제를 함께 처리한다.
3. 화질 자동 선택 재생기를 기존 릴스의 제한된 미리 읽기 정책에 연결한다. 원본 주소는 어떤 사용자 응답에도 포함되지 않게 한다.
4. 기존 공개 영상은 원본 백업과 변환본을 검증하고 재생 경로를 교체한 뒤, 기존 공개 주소·읽기 정책·전송 캐시까지 닫혔는지 검사한다. 이미 내려받은 원본을 회수할 수는 없다. 단순히 화면에서 주소만 교체해 놓고 완료로 처리하지 않는다.
5. 실제 iPhone Safari·Android Chrome에서 최초 진입, 준비된 다음 영상, 빠른 연속 넘기기, 역방향, 느린 연결, 백그라운드 복귀를 확인한다. 첫 프레임 시간과 전환 시간의 중앙값·느린 상위 구간, 재생 중 멈춘 비율, 시청 대비 전송량, 오류율, 한국 회선에서의 화질을 비교한다. 운영 성능 수치·절감률은 측정 전 확약하지 않는다.

원본 차단의 완료 조건은 비회원과 일반 회원 모두 원본 요청이 거부되며, 발행된 재생용 영상은 정상 재생되는 것이다. 속도 개선은 고화질 선택이 가능하다는 사실만으로 통과하지 않고 같은 영상·기기·회선의 전후 측정으로 판단한다.
