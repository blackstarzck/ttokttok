# IA 개편 1단계 — 릴스 탭 구현 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 영상 게시물만 보는 `/reels` 탭을 세운다. 홈은 이 단계에서 건드리지 않는다.

**Architecture:** 정렬 RPC에 **널 허용 타입 인자**를 더해 같은 랭킹 로직을 유형별로 나눠 쓴다. 널이면 지금처럼 전 유형을 섞으므로 홈은 한 줄도 바뀌지 않는다. 릴스 화면은 현재 홈과 같은 `FeedScroller` + `PostItem` 조합을 `type="video"`로 재사용한다 — 새 컴포넌트는 만들지 않는다.

**Tech Stack:** Next.js 16.3.3 App Router / React 19 / Supabase Postgres (plpgsql·sql RPC) / Tailwind v4 / lucide-react

## Global Constraints

- 설계 근거: `docs/superpowers/specs/2026-09-04-ia-restructure-design.md` — **결정 1·2·6·12**.
- **홈은 이 단계에서 동작이 바뀌지 않는다.** 타입 인자를 널로 넘겨 기존 순서를 그대로 재현해야 한다.
- **정렬 알고리즘을 바꾸지 않는다** (결정 12). 가중 랜덤 × 인기(ln 상한 [1,3]) × 신선도 × seen_penalty, 세션 시드 고정, 키셋 커서 — 전부 그대로다. 타입 필터만 더한다.
- **RPC 시그니처가 바뀌면 새 버전 이름을 만들고 옛 함수를 같은 마이그레이션에서 drop한다.** 이 저장소의 선례다 (`20260828000001`이 `get_feed_v3`를 만들고 `get_feed_v2(text, text, int, double precision)`를 drop했다). 기본값 있는 인자를 덧붙여 오버로드를 만들면 안 된다 — PostgREST는 RPC를 **이름 인자**로 호출하므로, 5개 이름으로 부르면 5인자 함수와 6인자 함수 양쪽에 맞아 `PGRST203` 모호성 오류가 난다.
- 스타일: 시맨틱 토큰만 (`bg-background`). 원시 hex·px·Tailwind 팔레트 직접 참조 금지. **예외**: 피드 위에 얹히는 크롬은 흰색 고정 구역이다 (`docs/DESIGN.md` Colors).
- `docs/DESIGN.md:155` verbatim: `터치 타깃 최소 44×44px, 인접 타깃 간 8px 이상.` **두 절 모두.**
- 상태·데이터: 서버 상태=TanStack Query / UI 상태=useState / URL 상태=searchParams. 전역 스토어 금지. 보안은 RLS가 담당.
- 서버 컴포넌트가 기본. `"use client"`는 최소 잎에만.
- 마이그레이션 파일명 규칙: `YYYYMMDDNNNNNN_<name>.sql`. 직전 파일은 `20260903000003_reply_addressee.sql`.
- **이 단계는 순수 함수를 추가하지 않으므로 새 단위 테스트가 없다.** 기존 56개가 그대로 통과하면 된다. 검증을 채우려고 빈 테스트를 쓰지 않는다 (`docs/FRONTEND.md` §7 — 순수 함수만 테스트, Supabase 쿼리 빌더는 모킹하지 않는다).
- 한국어 주석으로 **왜**를 적는다. 커밋 메시지는 한국어 + Conventional Commits.
- 문서와 코드가 어긋난 채 커밋하지 않는다 (`AGENTS.md` 완료 기준) — 스키마·IA를 바꾼 태스크가 **같은 커밋에서** PRD를 갱신한다.

- [ ] **Step 1: 마이그레이션 작성**

`supabase/migrations/20260904000001_feed_type_filter.sql`:

```sql
-- ============================================================
-- 정렬 RPC에 게시물 유형 필터 (IA 개편 결정 1·12)
--
-- 홈은 type='cards', 릴스는 type='video'만 본다. 두 화면이 같은 규칙으로
-- 각자 유형 안에서 정렬되도록, 정렬 로직은 그대로 두고 필터만 더한다.
--
-- p_type이 널이면 지금처럼 전 유형을 섞는다. 개편이 단계적으로 진행되는
-- 동안 홈이 기존 동작을 그대로 유지해야 하기 때문이다. 널일 때 weights는
-- 이전과 완전히 동일한 집합이므로, 홈의 순서는 한 톨도 바뀌지 않는다.
--
-- 새 이름으로 만들고 v3를 지우는 이유: 기본값 있는 인자를 덧붙이면
-- 교체가 아니라 오버로드가 된다. PostgREST는 RPC를 이름 인자로 부르므로
-- 5개 이름으로 호출하면 5인자·6인자 양쪽에 맞아 PGRST203(모호한 함수)이
-- 난다. 20260828000001이 v2를 지우고 v3를 만든 것과 같은 처리다.
--
-- 중앙값(baseline)이 필터 안쪽에서 계산되는 것은 의도한 바다 — 영상은
-- 영상들 사이의 중앙값과 비교돼야 한다. 유형별로 조회 규모가 다른데
-- 전체 중앙값을 쓰면 한쪽이 통째로 면제받거나 통째로 벌을 받는다.
-- ============================================================

create function public.get_feed_v4(
  p_seed text,
  p_session_id text default null,
  p_limit int default 10,
  p_cursor text default null,
  p_cursor_id uuid default null,
  p_type text default null
)
returns table (
  id uuid,
  cursor_token text
)
language sql
security definer
set search_path = public
set extra_float_digits = 3
stable
as $$
  with weights as (
    select
      p.id,
      p.published_at,
      p.view_count,
      -- [1, 3]으로 압축된 인기 가중 (조회는 좋아요보다 가볍게)
      1 + least(ln(1 + p.like_count + p.view_count * 0.1) / 4, 2) as popularity
    from public.posts p
    where p.status = 'published'
      and (p_type is null or p.type = p_type)
  ),
  baseline as (
    select percentile_cont(0.5) within group (order by popularity) as median
    from weights
  )
  select s.id, s.score::text
  from (
    select
      w.id,
      (
        -- [0,1) 결정적 난수 — 같은 seed면 순서가 재현된다
        (abs(hashtextextended(w.id::text || p_seed, 0) % 1000000000) / 1000000000.0)
        -- 인기 가중. 아직 평가할 만큼 노출되지 않은 글은 면제한다.
        * (case
             when w.view_count < 50
               then greatest(w.popularity, (select median from baseline))
             else w.popularity
           end)
        -- 신선도: 발행 7일 이내 보정
        * (case when w.published_at > now() - interval '7 days' then 1.5 else 1.0 end)
        -- 이미 본 글은 뒤로. 아예 빼지는 않는다 — 콘텐츠가 적을 때
        -- 피드가 비어 버리기 때문.
        * (case
             when p_session_id is not null and exists (
               select 1 from public.view_logs vl
               where vl.post_id = w.id
                 and vl.session_id = p_session_id
                 and vl.created_at > now() - interval '3 days'
             ) then 0.25
             else 1.0
           end)
      )::double precision as score
    from weights w
  ) s
  -- 정렬이 (score desc, id asc)이므로 다음 페이지는 그 뒤에 오는 것들이다.
  where p_cursor is null
     or s.score < p_cursor::double precision
     or (s.score = p_cursor::double precision and s.id > p_cursor_id)
  order by s.score desc, s.id
  limit greatest(p_limit, 0);
$$;

-- 옛 함수를 남기면 오버로드 모호성이 생긴다(위 주석).
drop function public.get_feed_v3(text, text, int, text, uuid);

-- 이웃 마이그레이션과 같은 형태로 권한을 명시한다. Supabase의 스키마 단위
-- 기본 권한이 이미 덮어 주지만, 그건 이 저장소가 선언한 것이 아니라 플랫폼
-- 기본값이다. 암묵적 기본값에 기대면 환경이 바뀔 때 조용히 깨진다.
grant execute on function public.get_feed_v4(text, text, int, text, uuid, text)
  to anon, authenticated;
```

커서는 점수 기준인데 점수 분포가 유형별로 달라진다. 페이지가 겹치거나 빠지지 않는지 본다.

```sql
with p1 as (
  select * from public.get_feed_v4('s', null, 5, null, null, 'cards')
),
last1 as (
  select cursor_token, id from p1 order by cursor_token::double precision desc, id offset 4 limit 1
),
p2 as (
  select f.* from last1, lateral public.get_feed_v4('s', null, 5, last1.cursor_token, last1.id, 'cards') f
)
select
  (select count(*) from p1) as page1,
  (select count(*) from p2) as page2,
  (select count(*) from p1 join p2 on p1.id = p2.id) as overlap,
  (select count(distinct id) from (select id from p1 union all select id from p2) u) as distinct_total;
```

기대: `page1 = 5`, `overlap = 0`, 그리고 `page1 + page2 = distinct_total = 발행된 cards 총 개수`. 시드 기준으로는 `page2 = 3`, `distinct_total = 8`이다. 데이터가 다르면 숫자는 달라지되 **겹침 0**과 **합계 = 총 개수**는 반드시 성립해야 한다. (읽기 전용 조회라 CTE 스냅샷 문제가 없다.)

  seed: string,

    p_cursor_id: cursor?.id ?? null,

- [ ] **Step 4: 릴스 화면**

`src/app/(main)/reels/page.tsx`:

```tsx
import type { Metadata } from "next";
import { cookies } from "next/headers";
import { FeedScroller } from "@/components/feed/feed-scroller";
import { PostItem } from "@/components/feed/post-item";
import { getFeed } from "@/lib/feed";
import { getCurrentUser, getLikedPostIds } from "@/lib/auth";
import { FEED_SEED_COOKIE } from "@/lib/feed-seed";

export const metadata: Metadata = { title: "릴스" };

/**
 * 릴스 — 영상 게시물만 보는 전면 피드 (IA 개편 결정 1·6).
 *
 * 화면은 현재 홈과 같은 조합(FeedScroller + PostItem)을 그대로 쓰고
 * 유형만 좁힌다. 전면 스냅·오버레이 크롬·영상 컨트롤이 이미 여기 맞춰져
 * 있어 새로 만들 것이 없다.
 *
 * 상단 바를 두지 않는다 (결정 8) — 알림 진입은 홈 헤더 하나로 충분하다.
 *
 * seed 쿠키를 홈과 함께 쓴다. 점수는 게시물별로 계산되므로 유형을 좁혀도
 * 같은 seed면 상대 순서가 유지된다 — 탭을 오가며 순서가 흔들리지 않는다.
 */
export default async function ReelsPage() {
  const jar = await cookies();
  const seed = jar.get(FEED_SEED_COOKIE)?.value ?? crypto.randomUUID();

  const { posts, nextCursor } = await getFeed(seed, null, 10, null, "video");

  const [user, likedIds] = await Promise.all([
    getCurrentUser(),
    getLikedPostIds(posts.map((p) => p.id)),
  ]);

  return (
    <FeedScroller
      postIds={posts.map((p) => p.id)}
      seed={seed}
      initialCursor={nextCursor}
      type="video"
    >
      {posts.map((post) => (
        <PostItem
          key={post.id}
          post={post}
          liked={likedIds.has(post.id)}
          isGuest={user === null}
          userId={user?.id ?? null}
        />
      ))}
    </FeedScroller>
  );
}
```

- [ ] **Step 7: 375px에서 확인**

영상 게시물이 2개뿐이라(시드) 스크롤 검증이 얕다. **먼저 영상 게시물을 6개 이상으로 늘려** 페이지네이션이 실제로 도는 상태를 만든다 — 기존 영상 게시물의 행을 복제하고 `id`만 새로 주면 된다.

1. GNB가 4칸(홈·릴스·탐색·프로필)으로 뜨고 라벨이 겹치지 않는다
2. 릴스 탭에 **영상 게시물만** 보인다 — 카드 게시물이 하나도 섞이지 않는다
3. 위아래 스냅 스크롤이 동작하고, 끝까지 내리면 다음 페이지가 붙는다 (프리페치가 `type="video"`로 나가는지 네트워크에서 확인)
4. 영상이 음소거 자동재생되고 탭하면 일시정지/재개, 우상단 음소거 토글이 동작한다
5. 좋아요·댓글·공유·읽기 CTA가 릴스에서도 동작한다
6. **홈은 이전과 똑같다** — 카드와 영상이 섞여 나오고 상단 바가 그대로 있다
7. 릴스에는 상단 바가 없다
8. GNB 활성 표시가 탭마다 맞게 바뀐다
9. 게스트로도 릴스가 보이고, 좋아요를 누르면 로그인으로 유도된다

> 이 단계에서는 홈이 아직 전 유형을 보여주므로 **영상 게시물이 홈과 릴스 양쪽에 나타난다**. 의도한 과도기다(설계 문서 단계표). 그동안 영상 조회가 두 화면에서 잡힐 수 있는데, 2단계에서 홈이 `type='cards'`로 좁혀지면 사라진다.
>
> 릴스 상단에 **96px 검정 스크림**이 남는 것도 과도기다 — 흰색 상단 바가 밝은 표지 위에서 읽히도록 넣은 것인데 릴스에는 그 바가 없다. 3단계에서 제거한다 (설계 결정 9). **이 단계에서 고치지 않는다** — 지금 걷으면 상단 바가 아직 살아 있는 홈이 깨진다.
>
> (`CHROME_SAFE_AREA`의 `pt-16`은 릴스에 영향이 없다. 그 상수는 `TemplateCard`·`CardPlaceholder`와 `post_videos`가 없을 때의 폴백만 쓰는데, 정상 영상 게시물은 셋 다 거치지 않는다 — DOM에서 `pt-16` 요소가 없고 `article` top이 0인 것을 확인했다.)

- [ ] **Step 8: PRD §4 갱신**

`docs/prd-ttokttok.md` §4의 트리에서 아래 네 줄을

```
├─ 홈 (/)               ← GNB 1. 세로 스크롤 숏폼 피드
│   └─ 게시물 상세 (딥링크 /p/[postId])
├─ 알림 (/notifications) ← 홈 상단 오버레이 바의 알림 종에서 진입 (GNB 아님, 로그인 필요)
├─ 탐색 (/discover)      ← GNB 2. 검색 + 추천 + 장르 칩 + 급상승
├─ 프로필 (/profile)     ← GNB 3. 학습 중 / 보관함 / 완독 / 활동 (로그인 필요)
```

이렇게 바꾼다:

```
├─ 홈 (/)               ← GNB 1. 세로 스크롤 숏폼 피드
│   └─ 게시물 상세 (딥링크 /p/[postId])
├─ 릴스 (/reels)         ← GNB 2. 영상 게시물만 보는 전면 스냅 피드
├─ 알림 (/notifications) ← 홈 상단 오버레이 바의 알림 종에서 진입 (GNB 아님, 로그인 필요)
├─ 탐색 (/discover)      ← GNB 3. 검색 + 추천 + 장르 칩 + 급상승
├─ 프로필 (/profile)     ← GNB 4. 학습 중 / 보관함 / 완독 / 활동 (로그인 필요)
```

홈 줄의 "세로 스크롤 숏폼 피드"는 **이 단계에서 바꾸지 않는다** — 홈은 아직 전 유형을 보여주므로 그 설명이 지금은 사실이다. 2단계에서 카드 전용이 될 때 고친다.
