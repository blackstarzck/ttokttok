# 대댓글 · 댓글 좋아요 · 알림 설계

2026-09-02. 그릴링 세션에서 확정한 17개 결정과 그 근거를 남긴다.
구현 계획은 `docs/superpowers/plans/2026-09-02-comment-threads.md`부터 단계별로 나뉜다.

## 배경

댓글은 있으나 평면이다 — `comments`에 `parent_id`가 없고, 좋아요도 없다.
PRD `:498`이 "대댓글, 댓글 좋아요"를 v2 백로그에 **한 묶음으로** 보류해 뒀고,
이번 작업이 그 보류를 푼다.

요청은 "대댓글을 넣고 UX는 인스타 릴스·유튜브와 똑같이"였다.
그런데 **두 레퍼런스는 핵심 지점에서 정반대로 동작한다.** 아래 선례 조사가
결정의 출발점이고, 갈릴 때마다 어느 쪽을 따랐는지 명시했다.

## 선례 조사 — 두 레퍼런스가 갈리는 지점

| 항목 | 인스타 릴스 | 유튜브(쇼츠) | 채택 |
|---|---|---|---|
| 답글 열람 | 인라인 확장 (시트 하나) | 푸시 패널 (시트 안 네비게이션 스택) | **릴스** |
| 스레드 깊이 | 1단 (형제로 flatten + @멘션) | 1단 (동일) | 동일 — 1단 |
| 답글 정렬 | 오래된 순 | 오래된 순 | 동일 |
| 부모 삭제 | 답글도 함께 사라짐 | "삭제된 댓글입니다" + 답글 유지 | **인스타** |
| 알림 묶음 | "○○님 외 4명" | 건별 | **혼합** (좋아요만 묶음) |
| 읽음 처리 | 진입 시 일괄 | 개별 탭 | **유튜브** |
| 딥링크 | 해당 댓글로 | 해당 댓글을 목록 최상단에 핀 | **유튜브** |
| 상단 바 | 릴스 탭엔 없음 / 홈 탭엔 로고 바 | 상단 벨 | 오버레이 상단 바 (릴스의 오버레이 방식 + 홈 탭의 로고 구성) |

**의도적으로 레퍼런스를 따르지 않은 지점 2개** (아래 "한계"에 근거):
`@멘션 없음`, `좋아요 목록을 도서 커버 그리드로`.

## 결정

### 댓글 · 답글

1. **답글 열람 = 인라인 확장.** 시트는 하나, 화면 전환 없음. 부모 아래
   들여쓰기된 채 접혀 있고 `답글 N개 보기`로 그 자리에서 펼친다.
   유튜브식 푸시 패널을 버린 이유: 시트 안에 네비게이션 스택이 생기면
   안드로이드 뒤로가기·`history` 엔트리·포커스 관리·스크롤 복원이 전부
   새 버그 표면이 된다. 480px 모바일 웹 + 책 발견 피드 규모에서 값을 못 한다.

2. **스레드 = 1단 고정.** `parent_id uuid references comments(id) on delete cascade`.
   모든 답글의 `parent_id`는 항상 최상위 댓글을 가리킨다.
   **1단 강제는 DB에서 한다** — `before insert` 트리거가 부모의 `parent_id`가
   NULL이 아니면 조부모로 되돌린다. 답글에도 답글 버튼이 있으므로(결정 8)
   클라이언트 버그로 3단이 생길 수 있고, 데이터가 한번 깊어지면 되돌리기 어렵다.
   무한 중첩을 버린 이유: 두 레퍼런스 모두 1단이고, 480px에서 3단 이상
   들여쓰기는 읽기가 무너진다.

3. **답글 로딩 = 펼칠 때 10개씩** 별도 요청. 더 있으면 `답글 더 보기`.
   최상위 로드 시 답글 미리보기를 동반하지 않는다 — 답글 있는 댓글이
   소수일 텐데 매 시트 열기마다 lateral join을 지불할 이유가 없다.

4. **답글 정렬 = 오래된 순 고정**, 토글 없음. 대화가 위에서 아래로 읽혀야 한다.
   최상위 댓글은 현행 최신순 유지.

5. **댓글 수 배지 = 최상위 + 답글 전체.** 기존 `sync_comment_count` 트리거를
   손대지 않는다 — 답글도 `comments` 행이라 자동으로 증감한다.
   배지가 12인데 시트를 열면 최상위가 5개만 보이는 상황은 두 레퍼런스도 같다.

6. **부모 삭제 = 연쇄 숨김.** 부모를 soft delete하면 답글도 함께 `deleted_at`.
   PRD §5.5의 "삭제된 댓글은 표시 없이 목록에서 제외" 규칙이 그대로 살고,
   자리표시자라는 새 UI 상태가 필요 없으며, 카운터 트리거가 행마다 발동해
   자동으로 맞는다. 어드민 `deleteReportedComment`에도 같은 연쇄를 적용한다 —
   신고당한 부모만 지우고 답글이 남으면 모더레이션이 무의미하다.

7. **@멘션 없음.** 들여쓰기만으로 구분한다. `mentioned_user_id` 컬럼도,
   본문 프리필도 두지 않는다.

8. **답글에도 "답글" 버튼이 있다.** 붙는 위치는 같은 부모 아래 형제다.

9. **최상위 댓글 = keyset 커서 + 더 보기 페이지네이션.** 현행 `.limit(100)` 평면을
   폐기한다. 피드의 `get_feed_v3` 커서 패턴을 따르되, 정렬이 단순
   `created_at desc`라 정렬점수 문자열 토큰(§11-37)까지는 필요 없다 —
   `(created_at, id)` 복합 키셋으로 충분하다.

10. **작성만 낙관적.** 댓글·답글 등록은 즉시 목록에 뜨고 실패 시 롤백+토스트.
    삭제·신고는 현행 invalidate+refetch 유지 — 빈도가 낮고, 연쇄 숨김을
    낙관적으로 재현하려면 클라이언트가 서버 로직을 복사해야 한다.
    레일 `comment_count` 배지는 로컬 델타로 즉시 반영한다(표시용 델타이므로
    "카운터는 트리거·RPC로만" 규칙 위반이 아니다).

11. **댓글 좋아요 추가**, 답글에도 붙는다. `comment_likes` + `comments.like_count`
    비정규화 + 트리거 (`posts` 패턴과 동일). 하트는 색이 아니라 **채움**으로
    구분한다 (DESIGN.md Colors).

### 알림

12. **진입점 = 홈 상단 오버레이 바.** 왼쪽 똑똑 로고, 오른쪽 알림 종 + 안 읽음 배지.
    홈 전용. **구조적 형제가 아니라 크롬 레이어**(`z-[3]`)로 넣어 §11-27
    ("홈의 구조적 형제는 하단 액션 바와 컨텐츠 영역 둘뿐")을 개정하지 않는다.
    유튜브식 상단 벨을 그대로 못 쓰는 이유: 홈 피드는 전면 영상이라 상단 바가
    없고, 구조적 헤더를 넣으면 스냅 높이가 바뀌며 릴스형 전면감이 깨진다.

13. **딥링크 = 핀 방식.** 해당 부모 댓글을 목록 최상단에 고정 렌더 + 답글 펼침
    + 대상 답글 하이라이트. 그 아래로 일반 목록.
    "댓글이 나올 때까지 로드 후 스크롤"을 버린 이유: 페이지네이션 깊이와
    무관하게 항상 성립하고, 왕복이 한 번이다.

14. **배지 갱신 = 60초 폴링 + 창 포커스 시.** 릴스형 피드는 라우트를 안 바꾸고
    계속 스크롤하므로 진입 시 조회만으로는 배지가 계속 0으로 보인다.
    Realtime은 하루 몇 건 볼륨에 WebSocket 상주가 과하고, 이 프로젝트에
    Realtime 선례가 아직 없다.

15. **읽음 = 개별 탭해야 읽음.** `read_at` 컬럼.

16. **묶음 = 좋아요만.** 답글 알림은 건별로 남긴다 — 묶으면 딥링크 목적지가
    여럿이 되어 결정 13이 성립하지 않고, 답글은 내용도 목적지도 제각각이라
    묶는 순간 정보가 사라진다.

17. **알림 대상 이벤트는 2종뿐이다.** 이 앱은 UGC가 아니라 게시물을 어드민이
    만든다(MVP 비목표). 따라서 "내 게시물에 댓글/좋아요"는 대상이 없다.
    남는 것은 (1) 내 댓글·답글에 달린 답글, (2) 내 댓글·답글에 눌린 좋아요.
    **본인이 본인에게 한 행위는 알림을 만들지 않는다.**

### 프로필

18. **활동 탭 추가** — 프로필 탭이 `학습 중 / 보관함 / 완독 / 활동` 4개가 된다.
    내부는 세그먼트 토글 2개: 좋아요는 도서 커버 3열 그리드(`BookmarkGrid`
    재사용), 댓글은 텍스트 목록.

## 데이터 모델 변경

```
comments
  + parent_id uuid NULL references comments(id) on delete cascade
  + like_count int not null default 0        -- 비정규화, 트리거만 증감
  index comments_parent_idx (parent_id, created_at)      -- 답글 오름차순 조회
  index comments_post_root_idx (post_id, created_at desc)
        where parent_id is null                          -- 최상위 키셋

comment_likes
  (user_id, comment_id) PK 복합, created_at
  -- user_id default auth.uid() (owner_defaults 관례)

notifications
  id uuid PK,
  recipient_id uuid FK profiles(id) on delete cascade,
  actor_id uuid FK profiles(id) on delete cascade,
  type text CHECK (type IN ('reply','comment_like')),
  comment_id uuid FK comments(id) on delete cascade,   -- 대상 댓글(답글이면 그 답글)
  post_id uuid FK posts(id) on delete cascade,         -- 딥링크용
  read_at timestamptz NULL,
  created_at timestamptz
  index notifications_recipient_idx (recipient_id, created_at desc)
```

**RLS**: `comment_likes`는 본인 행만 쓰기·전체 읽기(카운트는 비정규화 컬럼이
담당하므로 읽기는 "내가 눌렀나" 판별용). `notifications`는 `recipient_id =
auth.uid()`인 행만 select·update(읽음 처리), insert는 트리거(security definer)만.

## 발견된 파급 — 계획에 반드시 포함

1. **`CHROME_SAFE_AREA`의 상단 값이 무효가 된다.** 현재 `pt-5`(20px)에는
   *"피할 크롬이 없는 순수 시각 여백"* 이라는 주석이 붙어 있다. 상단 바가
   생기면 카드 본문이 로고·종 아래로 파고든다. 좌우·하단과 같은 산식
   (여백 + 바 높이 + 여유)으로 재계산하고 주석을 고친다.
2. **상단 스크림이 없다.** 현재 스크림은 하단 120px 한 장뿐이다. 흰색 고정
   크롬을 상단에 얹으려면 대비를 만들 상단 스크림이 필요하다. DESIGN.md의
   Colors 절(스크림 서술)과 `post-item.tsx` 둘 다 갱신 대상이다.
3. **PRD §5.5 갱신** — 댓글 표에 답글·좋아요 행 추가, 연쇄 숨김 규칙 명시.
   **PRD §5.7 갱신** — 프로필 탭이 3개에서 4개로. **PRD §11에 결정 기록 추가**
   (대댓글 모델 / 알림 도입 / 상단 바 / 활동 탭). **PRD `:498` v2 백로그에서
   "대댓글, 댓글 좋아요" 제거.**
4. **테스트 인프라가 없었다.** vitest·jest 모두 없고 `test` 스크립트도 없었다.
   이번 작업에서 Vitest를 도입했다 — 커서 페이지네이션·낙관적 캐시 갱신처럼
   순수 함수로 뽑아낸 로직이 늘면서 `npm run build` + 375px 확인만으로는
   회귀를 잡기 어려워졌다. 경계는 좁게 유지한다: 테스트는 순수 함수만
   대상이다. Supabase 쿼리 빌더는 모킹하지 않는다(PostgREST 체인 모킹은
   모킹 모양만 검증한다) — 네트워크 경로와 렌더는 여전히 `npm run build` +
   375px 뷰포트 확인이 맡는다(`FRONTEND.md §7`).

## 단계

각 단계는 그 자체로 동작하는 소프트웨어를 낸다.

| 단계 | 내용 | 계획 문서 |
|---|---|---|
| 1 | 대댓글 (스키마·연쇄 삭제·인라인 확장 UI·더 보기 페이지네이션 교체) | `plans/2026-09-02-comment-threads.md` — **완료·머지** |
| 2 | 댓글 좋아요 | `plans/2026-09-03-comment-likes.md` — **완료·머지** |
| 3 | 프로필 활동 탭 | `plans/2026-09-03-profile-activity.md` — **완료·머지** |
| 4 | 알림 시스템 | `plans/2026-09-03-notifications.md` — **완료·머지** |
| ~~5~~ | ~~홈 상단 오버레이 바 + 세이프존 재계산~~ → **4단계에 흡수** | 같은 계획의 Task 5 — **완료·머지** |

**5단계는 따로 진행하지 않았다.** 상단 바는 알림함으로 들어가는 진입점이라
알림 없이 먼저 만들면 아무 데도 닿지 않는 종이 된다. 그래서 4단계 계획의
Task 5로 합쳐 `top-bar.tsx`·`unread-badge.tsx`와 `CHROME_SAFE_AREA`의
상단값 재계산(`pt-5` → `pt-16`)을 함께 냈다. 결정 12가 이 단계를 규정한다.

계획을 미리 다 쓰지 않는 이유: 1단계에서 커서 페이지네이션과 낙관적 갱신의
캐시 구조가 정해지는데, 2~5단계가 전부 그 위에 얹힌다. 먼저 쓰면 다시 쓴다.

이 설계 문서가 다루는 범위는 여기서 끝난다. 이후 논의된 **IA 개편**(현재
전면 피드를 릴스/쇼츠 탭으로 옮기고 홈을 게시글 카드 피드로 전환)은
사용자가 "알림 먼저, IA는 별건"으로 정해 **별도 설계 대상**이다 — 이 문서의
결정들 위에 얹히는 것이 아니라 홈의 정체성을 바꾸므로, 그릴링부터 다시 한다.

## 기록해 둘 한계

1. **답글끼리의 대화 상대가 명시되지 않는다.** 결정 7(@멘션 없음)과
   결정 8(답글에도 답글 버튼)을 함께 택한 결과다. 한 스레드에 3명 이상이
   얽히면 누가 누구에게 한 말인지 UI가 말해주지 않고, 사용자가 본문에 직접
   "○○님"을 적어야 한다. 두 레퍼런스는 이 문제를 @멘션으로 푼다.
   되돌리는 비용: `mentioned_user_id` 컬럼 추가는 가산 마이그레이션이라 작다.

2. **활동 탭의 좋아요 그리드가 보관함과 거의 같아 보인다.** 둘 다 3열 도서
   커버 그리드다. 또한 §11-36(도서당 게시물 중복 허용) 때문에 같은 책의
   게시물을 여러 개 좋아요하면 같은 커버가 반복된다. 좋아요(가벼운 반응)와
   찜(나중에 읽을 것)의 역할 구분이 흐려질 수 있다.

3. **답글 알림이 그룹되지 않아 목록이 길어질 수 있다.** 결정 16의 대가다.
